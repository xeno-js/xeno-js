# Database

XenoJS keeps database access deliberately layered. The framework registers one
low-level `IDbClient` through `AppBuilder.addDb`, then lets your application
compose data sources, filter builders, mappers, repositories, and read DAOs
around it.

This section documents the PostgreSQL/Drizzle path generated by `@XenoJS/create`
and exposed by `@xeno`.

## Reading Order

1. [Setup](./setup.md): create a project with the database option enabled.
2. [Injection tokens](../dependency-injection/tokens.md): create `src/tokens.ts`
   before registering app services.
3. [Schema and bootstrap](./schema-and-bootstrap.md): define Drizzle tables and
   register them in the XenoJS container.
4. [Data sources](./datasources.md): use `HardDeleteDataSource`,
   `SoftDeleteDataSource`, and `ReadDataSource`.
5. [Filter builder](./filter-builder.md): implement an application-specific
   bridge from XenoJS criteria to Drizzle SQL.
6. [Repositories and DAOs](./repositories-and-daos.md): wire mappers, data
   sources, repositories, and read DAOs.

## Mental Model

The database flow is:

```text
AppBuilder.addDb()
  -> registers INJECTION_TOKENS.DB_CLIENT
  -> DrizzleDbClient executes select/insert/update/delete
  -> DataSource builds query conditions through IFilterBuilder
  -> Repository or ReadDao maps DTOs to domain entities
```

XenoJS does not require you to expose Drizzle throughout your application.
Drizzle stays in the infrastructure layer: schemas, filter builders, and the
database client. Your domain and application code can depend on repositories,
DAOs, and result types instead.

Before registering table-specific services, create a central `src/tokens.ts`
file for your application tokens. The database examples in this section assume
that repositories, data sources, mappers, and filter builders are registered
through tokens exported from that file.
